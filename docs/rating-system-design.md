# 人狼ゲームレーティングシステム設計書

## 概要

本ドキュメントは、人狼ゲームアプリケーションにおけるEloレーティングシステムの設計仕様を定義する。チェスのEloレーティングシステムを参考とし、対戦相手のレーティングと勝敗結果に基づいて公平で正確なレーティングを算出するシステムである。

## 1. システム概要

### 1.1 目的
- プレイヤーの実力を数値化し、成長を可視化する
- 適切なレベルのプレイヤー同士でマッチングする
- 戦略的なゲームプレイを促進する

### 1.2 基本方針
- **Eloレーティング方式**: チェスで使用される標準的なレーティングシステム
- **陣営戦評価**: 個人の勝敗は陣営の勝敗に依存
- **総合評価**: 全役職での総合的な実力を評価

## 2. レーティング計算方式

### 2.1 基本計算式

```
新しいレーティング = 現在レーティング + K × (実際の結果 - 期待値)
```

#### 期待値の計算
```
期待勝率 = 1 / (1 + 10^((相手レーティング - 自分のレーティング) / 400))
```

#### 実際の結果
- **勝利**: 1.0
- **敗北**: 0.0
- **引き分け**: 0.5（通常は発生しない）

### 2.2 K値（変動係数）の設定

| 経験レベル | ゲーム数 | K値 | 説明 |
|------------|----------|-----|------|
| 初心者 | 0-30 | 40 | 大きな変動で素早く適正レーティングに収束 |
| 中級者 | 31-100 | 20 | 中程度の変動で安定性を保ちながら調整 |
| 上級者 | 101-200 | 15 | 小さな変動でレーティングの安定性を重視 |
| エキスパート | 200+ | 10 | 最小変動でエキスパートレベルの安定性を確保 |

## 3. 勝敗判定システム

### 3.1 陣営勝利条件

#### 村人陣営勝利
- 人狼を全滅させた場合
- 妖狐が存在する場合は、妖狐も含めて全滅させる必要がある

#### 人狼陣営勝利
- 村人陣営の人数を過半数以下にした場合
- 村人陣営には村人、占い師、霊媒師、狩人、共有者が含まれる

#### 妖狐勝利
- 特定の条件を満たした場合（例：一定日数生存）
- 他の陣営とは独立した勝利条件

### 3.2 個人の勝敗判定

- **陣営勝利時**: その陣営の全員が「勝利」として扱う
- **陣営敗北時**: その陣営の全員が「敗北」として扱う
- **生存日数や貢献度**: 別途ボーナスポイントとして評価

## 4. データベース設計

### 実装状況

現在のスキーマファイル（`database/schema.dbml`）には、レーティングシステムの基本構造が実装されています。以下のテーブルが定義されています：

- **users**: レーティング、ゲーム数、勝利数を含む
- **user_role_stats**: 役職別の戦績を追跡
- **games**: ゲームの基本情報
- **game_players**: ゲーム参加者の役職情報
- **channels**: チャンネル管理
- **channel_messages / game_messages**: メッセージシステム

### 4.1 ユーザー総合レーティングテーブル

現在のスキーマでは、`users`テーブルに直接レーティング関連のフィールドが統合されています。

```sql
Table users {
  id uuid [pk, default: `gen_random_uuid()`, note: 'ユーザーID']
  username varchar(50) [not null, unique, note: 'ユーザー名']
  is_guest boolean [not null, default: true, note: 'ゲストユーザーフラグ']
  email varchar(255) [unique, note: 'メールアドレス（ゲストの場合はnull）']
  password_hash varchar(255) [note: 'パスワードハッシュ（ゲストの場合はnull）']
  avatar_url varchar(500) [note: 'アバター画像URL']
  bio text [note: '自己紹介文']
  rating int [not null, default: 1000, note: 'Eloレーティング（1000基準）']
  games_played int [not null, default: 0, note: '総ゲーム参加回数']
  wins int [not null, default: 0, note: '総勝利回数']
  deleted_at timestamp [note: 'ソフトデリート日時']
  created_at timestamp [default: `now()`, note: '作成日時']
  updated_at timestamp [default: `now()`, note: '更新日時']
  
  indexes {
    (email)
    (username)
    (is_guest)
    (rating)
  }
}
```

### 4.2 役職別戦績テーブル

```sql
Table user_role_stats {
  user_id uuid [not null, ref: > users.id, note: 'ユーザーID']
  role role_enum [not null, note: '役職']
  total_games int [not null, default: 0, note: '総ゲーム参加回数']
  victories int [not null, default: 0, note: '勝利回数']
  
  indexes {
    (user_id, role) [pk]
    (role, victories)
  }
}
```

このテーブルにより、各ユーザーの役職別の戦績を追跡できます。





## 5. レーティング計算フロー

### 5.1 ゲーム開始時

1. 各プレイヤーの現在レーティングを取得
2. 対戦相手の平均レーティングを計算
3. 各プレイヤーの期待勝率を算出

### 5.2 ゲーム終了時

1. 勝敗結果を判定（陣営勝利の判定）
2. 各プレイヤーの実際の結果を計算
3. Elo式でレーティング変動を算出
4. レーティングを更新

### 5.3 計算例

#### 例1: 同レベルの対戦
- プレイヤーA: 1500、プレイヤーB: 1500
- 期待勝率: 50% vs 50%
- プレイヤーAが勝利した場合
- レーティング変動: +20 (K=40の場合)

#### 例2: レーティング差がある対戦
- プレイヤーA: 1600、プレイヤーB: 1400
- 期待勝率: 76% vs 24%
- プレイヤーBが勝利した場合（下克上）
- プレイヤーBのレーティング変動: +30.4 (K=40の場合)
- プレイヤーAのレーティング変動: -30.4 (K=40の場合)

## 7. 実装上の注意点

### 8.1 レーティング保護

- **新規プレイヤー保護**: 最初の10ゲームは大幅なレーティング低下を防ぐ
- **長期不参加者**: 一定期間不参加の場合はレーティングを調整

### 8.2 不正対策

- **アカウント乗っ取り**: 異常なレーティング変動を監視
- **チート行為**: 不自然な勝利パターンを検出
- **レーティング操作**: 意図的な敗北によるレーティング操作を防止

### 8.3 パフォーマンス

- **バッチ処理**: レーティング更新は非同期で処理
- **キャッシュ**: 頻繁にアクセスされるレーティング情報をキャッシュ
- **データベース最適化**: インデックスの適切な設定
